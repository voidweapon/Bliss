# Root Thread Scheduling and Ownership

Accepted. Top-level Roots may be configured per Root type as `MainThread` or `DedicatedThread`; existing Server configurations and Unity remain on the World-driven main thread by default. A DedicatedThread Root owns one thread for its full lifecycle and update phases, while child Roots inherit the parent owner. World publishes update pulses with frame-time snapshots; each Root cycle uses its pulse's snapshot, while real-time queries remain real-time. A Root may hold at most one pending pulse, with excess pulses coalesced into the latest snapshot and counted. Blocking the World thread prevents new pulses, so isolation is guaranteed between DedicatedThread Roots only.

The RootManager remains the authoritative Root registry, while the scheduler owns execution. Initializing Roots process necessary initialization work but reject ordinary business requests until ready; failures clean up on the owner thread and fail Server startup. Cross-Root mutations are routed to their owner; ETTask remains single-threaded, and cross-thread lifecycle results return to the caller's owner before completing its task. Shared services are initialized before Root threads start and disposed after they stop; a join timeout fails shutdown rather than disposing dependencies still in use. Invalid configuration, startup failure, or an unhandled Root lifecycle or update exception fails the Server rather than silently falling back; handled business errors retain their protocol semantics.

This preserves single-thread ownership of mutable Root state while allowing configured Roots to progress independently without global phase barriers. Correctness and isolation tests are required; performance measurements inform explicit per-Root configuration but impose no automatic threshold. Thread-pool scheduling and full Server graceful shutdown remain separate future decisions.
