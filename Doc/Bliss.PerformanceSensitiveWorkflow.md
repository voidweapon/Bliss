# 性能敏感组件开发流程

新增、修改或优化性能敏感的组件、算法或影响复杂度的数据结构时，按以下顺序执行。根据实际组件选取场景，不把定时器的具体实现作为通用方案。

1. **明确行为和负载。** 确认公开接口、生命周期和必须保持的行为，以及性能目标、关键路径和代表性数据规模。识别正常与极端分布、稀疏与密集负载，并考虑空闲、取消、异常、重入和资源释放等适用场景。若有可比较的既有组件，确认双方功能和工作负载的可比范围；不要自行假定用户未要求的性能阈值。
2. **建立真实基准和基线。** 在 `BlissBenchMark` 中新增或更新 BenchmarkDotNet 基准，调用实际生产实现，覆盖选定的关键路径与规模，并验证基准确实执行了预期工作。对既有实现或可比较组件，在优化前实测并保存结果；全新组件没有既有基线时，记录这一事实，并在存在可比实现时测量它。比较双方使用相同输入、规模和运行环境，将准备工作排除在计时之外。无法运行真实实现时明确阻碍；模型或微基准只能作为补充，必须标明与生产路径的区别，不能冒充端到端结果。
3. **定位瓶颈。** 依据基线、复杂度分析和适用的性能剖析工具提出可验证的热点假设，逐项测量或实验，区分测得的事实和源码推断。检查数据分布、遍历、插入与删除、分配及生命周期检查的实际成本；不凭数据结构名称断定性能。
4. **保护行为并优化。** 在真实调用接缝补充回归测试，覆盖受改动影响的行为和边界；针对已确认的热点实施改动，保留约定的顺序、取消、异常恢复、重入及生命周期语义等适用约束。按项目注释规范解释非直观的性能设计和必要取舍。
5. **复测并交付。** 使用与基线相同的负载和测量条件重跑基准，比较优化前后及可比组件的耗时、分配等相关指标；运行相关测试、构建和分析器检查。检查基准警告、样本量和波动，必要时增加测量或注明结论不确定性；说明未覆盖的路径、剩余瓶颈和空间与时间的取舍。向用户报告实际数据、环境和限制；如基线、验证或目标未能完成，明确说明而非宣称完成。
