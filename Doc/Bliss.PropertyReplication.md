# UE5风格属性同步框架设计方案

> 归档日期：2026-06-21

## 概述

在现有消息分发与 MemoryPack 链路上，采用"服务器权威 + 分层可靠通道 + 增量属性复制"方式演进：先补齐属性复制元数据与脏标记，再引入批量复制与 ACK 窗口，最后接入快照重同步与客户端平滑校正，避免一次性重构网络底层。

**核心约束**
- 权威模型：服务器权威，客户端仅做预测显示
- 通道策略：关键属性走可靠通道，高频非关键属性走非可靠通道
- 交付范围：架构与接口草案（不含实现代码）

---

## 实施步骤

### Phase 1 — 复制模型与协议骨架（阻塞后续）

1. 以 SceneActor 相关组件为第一批复制对象（Transform / 运动状态 / 战斗核心状态），定义稳定的"可复制属性清单（PropertyIndex 不变更语义）"。
2. 设计复制通道分层：
   - **Reliable 通道**：关键状态（创建 / 销毁 / 生命值 / 控制状态）
   - **Unreliable 通道**：高频非关键状态（位置 / 速度 / 朝向）
3. 约束消息兼容策略：新增消息只追加字段，不改变既有 MemoryPackOrder；新增 opcode 使用独立保留区间。*depends on 1, 2*

### Phase 2 — 服务端复制核心（MVP 主干）

4. 建立 **ReplicatedPropertyRegistry**：维护"组件类型 → 可复制属性描述（Index / 类型 / 通道 / 频率 / 发送条件）"。
5. 引入 **DirtyMask + LastAckState**：属性写入时打脏；每个客户端维护已确认版本与最近发送窗口。*depends on 4*
6. 实现 **ReplicationScheduler**：按优先级和字节预算挑选脏属性，按 Actor 聚合后批量发送。*depends on 5*
7. 在现有 Map 广播辅助层扩展"按连接差异化复制"，替代纯广播。*depends on 6*

#### ReplicatedPropertyRegistry 设计展开

- **职责边界**
  - 把“某个组件有哪些属性可复制”收敛成稳定元数据目录，供调度器、校验器和协议生成器共用。
  - 不负责脏标记、不负责发送、不负责客户端应用，只负责登记、查询与校验。
  - 作为复制链路的唯一属性目录，避免属性信息散落在各个系统里。

- **核心数据**
  - `ComponentTypeId`：组件类型标识。
  - `PropertyIndex`：组件内局部索引，语义稳定，不随字段重排变化。
  - `PropertyType`：值类型信息，用于序列化与兼容性检查。
  - `Channel`：Reliable / Unreliable。
  - `FrequencyPolicy`：每 tick、按阈值、按事件触发等。
  - `SendCondition`：仅 owner、仅观察者、仅变化时发送等。
  - `DefaultReplicationMode`：首次加入时采用全量快照还是增量起步。

- **查询方式**
  - 按 `ComponentTypeId` 取整表，给调度器快速枚举该组件的复制字段。
  - 按 `PropertyIndex` 反查元数据，给写入路径和校验逻辑定位字段。
  - 按通道筛选，避免把关键属性和高频属性混在同一个发送集合里。

- **注册策略**
  - 每个可复制组件在初始化阶段完成注册，注册结果只读。
  - 注册时检查重复索引、类型不一致、通道缺失和条件冲突，失败即暴露配置错误。
  - 不允许运行时动态改写索引语义，避免协议漂移。

- **协作关系**
  - `DirtyMask` 依赖 Registry 提供位图映射。
  - `ReplicationScheduler` 依赖 Registry 提供属性优先级、通道和发送条件。
  - 协议哈希工具依赖 Registry 输出稳定顺序与签名。

- **演进原则**
  - 采用“组件内局部索引 + 组件类型 ID”组合治理，避免全局大表频繁冲突。
  - 为后续扩展预留索引空间，保证新增属性不破坏旧语义。
  - Registry 最终由编译期生成静态表提供，运行时只读查询。

#### DirtyMask + LastAckState 设计展开

- **DirtyMask 职责**
  - 记录单个可复制对象在当前 tick 内哪些属性发生了变化。
  - 只表达“脏/干净”，不保存值本身，也不关心发给了谁。
  - 作为调度器的第一层筛选条件，避免每次都扫描整表。

- **触发模型**
  - 采用“写入时 Push 打脏 + 调度时 Pull 校验”的混合方案。
  - Push 负责低成本标记变化，Pull 负责在发送前结合优先级、预算和 ACK 状态做二次确认。
  - 这样既避免全量扫描，也能防止漏脏和误脏。

- **DirtyMask 形态**
  - 以组件内 `PropertyIndex` 映射位图位数，并与 Registry 的索引保持一致。
  - 支持按属性打脏、按通道分组打脏、按整组件清空。
  - 对高频属性允许重复打脏，最终由调度器合并成一次发送。

- **手动打脏**
  - 除自动打脏外，保留手动打脏入口。
  - 用于派生状态变化、批量改值、外部系统直接改内存，以及“值没变但语义已变”的刷新场景。
  - 手动打脏必须走同一套 Registry 索引映射，不能绕过元数据目录。

- **LastAckState 职责**
  - 记录“某个连接对某个 Actor / 组件 / 属性窗口确认到哪里”。
  - 保存已确认版本、最近发送版本、未确认窗口和最后一次成功回执时间。
  - 用于判断重发、跳过和触发重同步，不直接参与业务计算。

- **LastAckState 形态**
  - 以连接为维度分表，避免一个连接丢包影响所有客户端。
  - 细分到 Actor 级别，必要时再拆到组件或属性窗口。
  - 同时维护可靠通道与非可靠通道的独立进度，避免互相阻塞。

- **协作流程**
  - 属性写入时先按 Registry 找到位图位，再设置 DirtyMask。
  - 调度器从 DirtyMask 中挑出待发属性，结合 LastAckState 决定发送增量还是补发。
  - 客户端回 ACK 后推进 LastAckState，已确认窗口中的位可以清理或降级。

- **增量差异快速比较（属性集 A vs B）**
  - 默认链路固定为 `version -> group hash -> bitmask XOR -> 实值编码`。
  - 第一层：组件级版本号，先快速跳过完全未变的对象。
  - 第二层：属性组 hash，缩小到具体变化组，避免整组件深扫。
  - 第三层：位图 `XOR`，将“本地脏位图”与“连接已确认位图”按机器字异或，快速得到候选差异集合。
  - 第四层：对候选属性做最终值编码，仅对进入发送预算的字段序列化。
  - 通道分桶在进入上述链路前完成，Reliable / Unreliable 分开处理。

- **推荐默认实现**
  - 以 `ulong` 位图作为主索引容器，按 64 位块扫描非零字。
  - 每组件维护 `LastWriteVersion`，每属性组维护 `GroupHash`，每属性维护 `LastSentVersionByConnection`。
  - 只对进入发送预算的属性做最终值序列化，未入预算保留在待发集合。

### ReplicationScheduler 设计

- **职责**
  - 把 `DirtyMask + LastAckState + Registry` 转成每连接可发送的批量复制包。
  - 不负责脏标记、不负责协议解析，只负责候选选择、排序、预算控制和批量封包。
  - 保持“同一连接内顺序稳定、不同连接之间可独立退化”。

- **输入**
  - `DirtyMask`：当前 tick 的脏属性集合。
  - `LastAckState`：连接已确认窗口、未确认窗口和最近发送位置。
  - `Registry`：属性优先级、通道、发送条件、分组信息。
  - `Budget`：每连接字节预算与每 tick 最大包数。

- **调度阶段**
  - **收集**：按连接拉取脏属性候选，先按通道分桶，再按 Actor 聚合。
  - **筛选**：结合 `LastAckState` 丢弃已确认且未变化的字段，保留待补发和新脏字段。
  - **排序**：按可靠性、业务优先级、变化频率、上次发送时间进行稳定排序。
  - **封包**：按 Actor 组装批量消息，直到字节预算耗尽为止。

- **优先级规则**
  - 可靠通道优先于非可靠通道，但非可靠通道不能长期饿死。
  - 关键状态优先于高频视觉状态。
  - 同一 Actor 内先发权威状态，再发预测/修正状态。

- **预算与退化**
  - 单连接预算不足时，优先保留关键状态和未确认窗口补发。
  - 超预算的属性保持在待发集合，下个 tick 重新参与调度。
  - 对持续高压连接启用降采样或分片发送，避免拖垮整轮 tick。

- **去重与稳定性**
  - 同一属性在同一 tick 只入队一次，后续写脏只更新版本，不重复扩展包体。
  - 同一 Actor 的字段尽量连续打包，减少消息头开销。
  - 调度顺序固定，避免同样输入在不同 tick 产生不同包顺序。

- **输出**
  - 每连接的复制包集合。
  - 每 Actor 的发送结果与未发送剩余项。
  - 供 `LastAckState` 回写的发送版本和窗口信息。

- **协作边界**
  - 只消费已确认的 Registry 元数据，不直接读业务对象字段。
  - 调度过程中不修改业务值，只生成发送计划。
  - 发送失败后不回滚业务状态，只回退发送进度和窗口记录。

- **重发与恢复**
  - 若连续若干个窗口未确认，则标记为“窗口失配”。
  - 窗口失配优先走局部补发，超出阈值再触发快照重同步。
  - 重发只针对未确认窗口，不回扫所有历史状态。

- **边界约束**
  - 服务器仍是最终权威，客户端不能直接提交最终权威状态。
  - 客户端允许上行“自治对象白名单属性”，服务器通过校验后再写入权威状态并触发 DirtyMask。
  - 客户端本地可以维护待上行的本地脏标记，但服务端 DirtyMask 只由服务端写入路径驱动。
  - LastAckState 必须按连接隔离，不能共享全局确认进度。
  - 任何 ACK 处理都必须幂等，重复回包不能推进错误窗口。

- **客户端自治属性上行约束**
  - 白名单属性必须在 Registry 中显式标记为 `ClientAuthCandidate`，默认关闭。
  - 首批仅放行 Transform 相关属性（位置、朝向）。
  - 上行包需要携带客户端本地 tick、序号和可选输入上下文，便于服务器做时序校验。
  - 服务器校验至少包含：对象归属校验、数值范围校验、变化速率校验、冷却/状态机校验。
  - 校验失败时不落库，并返回校正包覆盖客户端预测状态。
  - 校验通过后由服务器统一写入权威属性，再进入常规复制与 ACK 流程。

### Phase 3 — 客户端应用与校正（可与 Phase 2 后半并行）

8. 建立 **PropertyApplyPipeline**：按 Actor 与序列号有序应用，丢弃旧包，缺包触发窗口内补齐。*depends on 6*
9. 复用现有平滑机制并接入复制时间戳：关键状态可靠覆盖，Transform 类状态继续预测 + 纠偏。*depends on 8*
10. 增加 **ReSync 流程**：ACK 窗口超时或版本差过大时，触发单 Actor 或分片快照重同步。*depends on 8*

### Phase 4 — 工具化与治理（可与 Phase 3 并行）

11. 在协议生成流程增加"属性索引一致性检查"和"客户端 / 服务端协议哈希比对"，防止两端字段顺序漂移。
12. 增加可观测指标：每连接复制字节、丢包重发率、平均纠偏距离、属性命中率。

### Phase 5 — 增量迁移

13. 先迁移 Transform / 运动属性，验证稳定后再迁移战斗属性；旧消息保留灰度期并双写比对。*depends on Phase 2–3*

## 验证策略

1. **协议一致性**：比对两端 opcode 映射、字段顺序、协议哈希，必须完全一致。
2. **性能压测**：100 / 500 / 1000 实体三档，验证复制字节和服务端 tick 开销在预算内。
3. **网络鲁棒性**：注入 5%–20% 丢包，验证 ACK 窗口重传后关键属性最终一致。
4. **体验验证**：50 / 100 / 200ms 延迟下评估平滑抖动与纠偏距离。
5. **回归验证**：旧同步流程可继续运行，灰度双写结果一致。

## 延伸考量

1. **PropertyIndex 治理**：采用"组件内局部索引 + 组件类型 ID"组合键，避免全局大表频繁冲突。
2. **迁移节奏**：先双写 1–2 周观测再切主，避免一次切换造成线上定位困难。
3. **ACK 窗口**：先固定窗口长度与重传次数，稳定后再做自适应带宽控制。
