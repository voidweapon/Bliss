# LevelScene 初始化事务方案（备选）

> 状态：此前讨论的备选方案，不再作为首选或当前实施要求。首选方案及两者比较见 [LevelScene 显式初始化与启用流程](Bliss.LevelSceneInitializationFlow.md)。本方案尚未整体实施；当前代码仍使用 `DeferUntilCommit(Action, Action)` 和 `AfterCommit(Action)`，不能将本文视为现有行为保证。以下重试、快照、通知等约定仅属于此备选方案，不能直接视为首选方案的要求。

## 目标与边界

- 消除初始化事务中调用方传入的 `Action` 闭包，包括延迟生效、补偿和提交后工作；不是消除补偿逻辑。采用有类型的操作，由事务协调流程，各操作负责自身生效、部分失败状态和安全清理。
- 不提供隔离性：提交操作逐项生效期间，外部可能看到部分效果；提交失败后也不能保证外部未曾观察到这些效果。快照和通知是观察事务状态的推荐入口，不能阻止其他代码直接读取原始对象。
- 外部不得写入临时 LevelScene 及其临时对象；本阶段依靠约定，不通过 API 强制。外部必须接受清理后临时引用失效。已有共享状态允许外部修改，发生冲突时不覆盖其修改。
- 先以 LevelScene 初始化期间的 Actor AOI 注册打通类型化操作、补偿和通知，再逐项迁移其余调用；迁移期间保留尚未替换的旧路径，不宣称所有闭包已消除。

## 事务生命周期

1. `Create` 校验参数和取消状态。调用前 token 已取消时直接失败，不创建事务、场景或发送事务通知。
2. 事务创建后、构造根 `LogicScene` 前登记场景创建意图，包括父节点当时的 `InstanceId`、场景 ID、类型和名称。构造成功后补充场景 `InstanceId`；构造失败时仍能报告该意图。
3. 初始化阶段创建场景和资源，登记提交操作及提交后工作，但不执行提交操作。进入提交前冻结两类列表；之后不能追加独立操作。
4. 所有场景初始化完成且事务未失败时进入 `Committing`，发送通知，再按登记顺序逐项执行提交操作。`Apply` 可使用 ETTask 异步执行，严格等待前一项结束。每次恢复执行时检查事务和相关对象的生命周期；在切换为 `Committed` 前检查取消。
5. 所有提交操作成功后切换为 `Committed`，移交初始化资源的正常释放责任，立即发送事务完成通知，然后顺序执行提交后工作。根 `Create` 等待工作队列处理结束后返回或报告其失败。
6. 初始化、构造、提交或提交前取消失败时，事务不能提交；按本方案清理后发送一次 `Aborted` 或 `CleanupFailed` 完成通知，根 `Create` 抛出异常。清理失败时保留原始失败和清理失败原因，不等待后台重试。

状态至少区分 `Initializing`、`Committing`、`Committed`、`Aborting`、`Aborted` 和 `CleanupFailed`；具体类型与转换检查在实现时确定。进入 `Aborting` 后临时场景不可继续使用，先确定状态再清理，不能把清理失败表述为回滚成功。

## 嵌套与取消

- 根场景和嵌套场景共享事务及其操作顺序。允许 A 等待创建 B、B 再等待创建 C 的单条异步调用链；禁止同时存在尚未完成的并发嵌套分支。ETTask 的单线程异步等待仍可能交错，必须显式检查；违反约束立即抛异常并使共享事务失败。
- 嵌套 `Create` 在自身初始化结束后可以返回临时场景，不等待根事务提交，否则外层等待内层时会死锁。只有事务根 `Create` 等待整体提交和提交后工作。
- 内层失败或被取消立即标记共享事务失败并拒绝登记新操作；即使外层捕获异常也不能提交。等待外层初始化流程退出后，由根事务统一清理和通知。
- `Create` 调用方可传入 `ETCancellationToken`；任何嵌套调用取消都使共享事务失败。`Committed` 是取消边界：此前观察到取消则失败并补偿，此后调用方 token 不影响结果或提交后工作。`Committing` 通知后、第一个 `Apply` 前也要检查取消。
- `Apply` 收到取消后，在非 Root 关闭的情况下等待当前操作实际结束，再开始补偿；补偿使用独立的取消控制。token 是协作式取消请求，不证明底层操作已停止。不支持底层取消的操作未结束前禁止重试。

## 类型化操作与资源

- 每项操作有明确类型和状态，保存生效及清理所需的身份、句柄和进度。调用 `Apply` **之前**登记补偿责任；即使部分生效后抛异常，也必须能够识别已执行步骤。`Apply` 可以更新自身清理状态，但不能新增独立事务操作。
- 初始化期间取得的资源也纳入事务清理。在开始获取前登记清理责任，逐步记录已取得的句柄，以处理部分获取失败。类型化清理操作可复用现有销毁或卸载机制，但必须避免事务清理与场景 `Dispose` 重复释放。
- 初始化资源清理和已开始的提交操作补偿按实际取得或生效顺序统一逆序执行。清理可以异步，严格等待一项完成后再执行下一项。提交成功后，初始化资源的所有权移交给场景或资源管理器，正常销毁不再由事务负责。
- 普通业务路径不因存在该机制而自动加入事务：只有 LevelScene 初始化事务中的 Actor 延迟 AOI 注册；其他 Actor，包括事务提交后在 LevelScene 中创建的 Actor，继续立即注册。应沿所属关系识别有效初始化事务，覆盖嵌套普通子场景。

## 失败、冲突与重试

- 首次清理和后续重试均逆序执行，遇到第一项失败立即停止；已成功清理的项不再执行，保留失败项及尚未清理项和重试所需的最小现场。
- 清理结果区分成功、可重试失败、冲突；未预期异常按无法确认安全处理，停止自动重试并上报。允许暂时无法可靠检查冲突的操作加入事务，但补偿时无法证明安全即视为冲突。
- 清理共享状态前必须证明不会覆盖或删除外部变更。检测到冲突或无法证明安全时立即中断，报告 `CleanupFailed` 并告警；不尝试解决复杂资源依赖。冲突不自动重试；人工处理冲突后可请求重试，仍须通过安全检查，不提供强制覆盖或删除。
- 可重试失败由内部清理管理器按配置的有限次数和间隔自动重试；耗尽后保留记录并告警，等待人工触发。每项清理必须支持安全重试，同一事务已有清理或重试进行时拒绝新的重试请求。
- `CleanupFailed` 期间保留每个受影响场景的 `(parentInstanceId, sceneId)` 占用，禁止同一父节点生命周期下重建同 ID 场景；全部清理成功后释放。保存的是父节点销毁前的实例身份值，不依赖可被对象池复用的引用。跨父节点生命周期的共享资源仍须进行冲突检查。
- 清理记录仅存于内存。Root 关闭时可请求取消、停止等待并放弃剩余记录，不保证跨重启清理；迟到结果不得访问已销毁或复用的 Root，也不得再发送恢复通知。

## 快照和通知

- 对外观察使用独立值快照，不包含 `Entity`、组件、可变集合或异常对象引用。每次通知生成独立副本，后续状态变化不修改已有快照。
- 场景快照至少包含父节点 `InstanceId`、场景 ID、可为空的场景 `InstanceId`、类型和名称，以及自身初始化结果；未成功构造标记为 `NotCreated`。错误信息仅保存类型、消息和堆栈文本。事务结果与场景自身初始化结果分开，初始化完成不等于提交。
- 第一个提交操作生效前发送一次 `Committing` 通知，包含事务 ID 和全部已登记场景快照；通知后、第一个 `Apply` 前检查取消。该通知不能证明具体外部副作用属于该事务。
- 整个共享事务只发送一次完成通知，包含事务 ID、最终结果及所有场景快照。结果为 `CleanupFailed` 时，后续清理全部成功再发送一次独立的 `CleanupRecovered` 通知，使用同一事务 ID；这不改变失败结果。外部不支持事后查询或重放，观察者须在通知前订阅。
- 通知同步逐个发送，单个处理器异常分别记录和上报，不阻止其他处理器或改变事务结果。通知前先固定相应状态、ID 占用和清理记录，防止重入看到不一致的协调器状态。通知仅送达当时在线且已订阅的观察者，不持久化。

## 提交后工作与卡住监测

- 提交后工作也改为有类型的工作，不保存 `Action` 闭包。事务完成通知在队列执行前发送；队列按登记顺序执行并严格等待每项完成或失败。
- 工作失败只记录和上报，不回滚已提交事务，也不阻止后续工作。队列处理完后若有失败，根 `Create` 抛出明确表示“场景已提交但部分提交后工作失败”的异常，携带事务 ID、场景身份和各项原因；调用方不得将其当成未提交失败而重建或销毁场景。
- 不为每个步骤增加自动超时取消、中断或重试。独立于被等待操作的 Root 级监测器，在异步等待超过配置阈值时每次操作告警一次，记录事务 ID、阶段、操作类型和耗时；结束后记录恢复，不重复刷屏。操作继续等待，不能因为告警启动下一项或重试。
- 单线程同步阻塞会使同线程监测器无法运行；监测同步卡住、独立线程或进程级监控不在本阶段范围。

## 分阶段实施与验收

1. **AOI 纵向切片**：实现事务协调、类型化 AOI 注册/补偿、必要的通知和快照。现有 `AoiManager.Register` 可能在返回 identifier 前部分修改索引或触发可见关系回调；必须先设计可追踪的部分注册状态及安全补偿。公开可变条目不能假定版本号足以证明安全；无法证明时按冲突处理。可见关系回调已产生的外部副作用是否能够安全补偿，必须盘点和验证，不能假设注销等同于撤回观察者行为。
2. **逐项迁移**：盘点并迁移 Root 实体注册、SceneActor 管理、GameplayWorld 组件、物理 Timer、PhysX 资源、Unity 场景以及提交后通知和工作；明确所有权、部分失败、冲突检查、异步结束和现有 `Dispose` 的交互。
3. **兼容与验证**：区分未提交失败与已提交但后续工作失败；验证嵌套串行、捕获内层错误、取消边界、通知重入、补偿中断和人工重试、实例复用、Root 关闭及迟到结果。验证初始化期资源和提交期操作的统一逆序清理，并确认非事务 Actor 立即注册。

涉及 AOI、调度器或其他性能敏感路径的更改，执行 [性能敏感组件开发流程](Bliss.PerformanceSensitiveWorkflow.md)，使用真实生产路径建立基线、测试和基准，不能用模型基准替代。
