# 工作区代码审查流程

本文是 Bliss 项目内的审查补充约定，不修改或依赖修改用户目录、插件目录或其他第三方技能。使用外部审查技能时，沿用其标准与规格双轴审查方式；本文件规定审查尚未提交的项目改动应如何确定补丁范围和内容。

## 工作区模式

1. 在审查开始时固定基点为完整 commit hash，并记录该基点和本次审查的精确文件范围。基点应由用户指定；未指定时先询问。
2. 只纳入本次工作的已跟踪改动。用 `git diff <base-hash> -- <selected-tracked-paths>` 生成从基点到当前工作树的补丁。此命令同时覆盖暂存和未暂存改动，不要再拼接 `git diff --cached`，以免重复。
3. 未跟踪文件只有在用户明确选择后才纳入。确认它未被 Git 跟踪且未被忽略，并将完整文件内容作为新增文件补丁纳入审查。可用 `git diff --no-index -- /dev/null <path>` 生成补丁；差异存在时退出码为 1。未暂存的重命名通常表现为旧跟踪路径的删除和新未跟踪路径的新增，需显式纳入两者。
4. 排除未选择、忽略及生成文件。若所选文件内混有无法区分的既有改动，先向用户确认范围，不要擅自纳入或丢弃。
5. 启动审查前保存完整补丁和所选范围的状态快照；向审查者提供该快照，而不是假定其读取到的实时工作树与之相同。审查完成后重新采集并比较状态和补丁；如果有变化，废弃旧结论并审查新快照。
6. 明确报告基点、文件范围和补丁是否为空。空补丁应直接报告，不得为获得差异而暂存或提交。审查过程不得更改用户文件、暂存状态或创建提交。

已提交提交范围的审查继续使用外部审查技能原有的固定点与提交差异流程，不由本文替代。

## 提交前审查与验收

实现完成后，在征求提交批准前审查最终工作区补丁。根据审查结果修复后，必须对更新后的完整补丁重新审查；完成最终审查后，再展示变更和拟提交信息并征求明确批准。没有明确批准不得创建提交。

工作区流程的验收场景包括：暂存与未暂存改动同时存在、同一文件两类改动不重复、选定与未选定的未跟踪文件、暂存重命名、未暂存重命名、删除、空范围、范围外文件排除，以及审查前后暂存状态不变。
