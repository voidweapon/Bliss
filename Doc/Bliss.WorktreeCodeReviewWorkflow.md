# 工作区代码审查流程

本文是 Bliss 项目内的审查补充约定，不修改或依赖修改用户目录、插件目录或其他第三方技能。使用外部审查技能时，沿用其标准与规格双轴审查方式；本文件规定审查尚未提交的项目改动应如何确定补丁范围和内容。

## 快照工具与本地检查

使用仓库工具 `Tools/CodeReview/review_snapshot.py` 固定审查输入。任务开始时记录基点；用户未指定其他基点时，使用任务开始时的 `HEAD` 完整 commit hash。审查范围是本次改动中的精确文件路径，不把整个目录或工作区状态不加区分地纳入补丁。

```bash
base_commit="$(git rev-parse HEAD)"
python3 Tools/CodeReview/review_snapshot.py capture \
  --base "$base_commit" \
  --tracked path/to/changed-file.cs \
  --untracked path/to/new-file.cs \
  --output /path/to/new/review-snapshot
```

每个选定文件重复对应的 `--tracked` 或 `--untracked` 参数。输出目录必须不存在。工具只读取 Git 状态并写入指定输出目录，不暂存、清理或修改源码；忽略文件不能作为未跟踪文件纳入。将同一路径同时作为 tracked 与 untracked 选择，仅用于捕获“已暂存删除、随后在工作树重建为未跟踪文件”的删除与替换内容。文件路径被目录及其子文件取代时，工具拒绝该路径，避免把子项意外扩展进精确文件范围。空补丁直接报告，无需启动审查。快照包含完整补丁、基点与 HEAD、显式范围、所选文件状态和 SHA-256，以及待填写的 `review-record.md`。

```bash
python3 Tools/CodeReview/review_snapshot.py verify /path/to/review-snapshot
bash Tools/CodeReview/check-local.sh
```

将快照及其 `review-record.md` 一并提供给审查者。`verify` 在开始审查前和发布结论前各运行一次，确认 HEAD、所选文件 Git 状态、暂存区条目/内容及补丁摘要均未变化；快照中的补丁和裁定记录也必须存在且可读。文件状态即使补丁内容未变，只要暂存状态变化，也视为快照过期。若过期，基于当前状态重新 capture，并让结论对应新快照。审查期间发现源码需要修复时，先完成本轮修复，再建立新的最终快照。

`check-local.sh` 根据 `Unity/Packages/packages-lock.json` 解析 Unity Mathematics 版本，并要求本地缓存中恰好有一个版本匹配且包含运行时程序集的包。随后先运行快照工具测试，再按 `.github/workflows/dotnet-ci.yml` 的顺序运行 Server 构建、Analyzer 单测、单元测试和 GameplayIntegration 测试；需要该依赖的命令显式使用锁定版本，任何步骤失败立即停止。它需要 Python 3、Git、.NET 8、还原所需的 NuGet 包及锁定版本的本地 Unity Mathematics 包缓存；依赖缺失或环境失败应报告为未通过，不得跳过并宣称通过。

## 问题裁定记录

每次快照的 `review-record.md` 是该次审查及其后续复审的记录。首次审查后填写发现及裁定；后续 capture 使用 `--prior-record /path/to/previous/review-record.md`，把已有记录原样带入新快照，避免丢失已解决争议。

每个发现使用稳定 ID，并记录审查轴（Standards 或 Spec）、文件与行号、引用的规范或需求、问题描述、裁定、证据/理由和当前状态。裁定使用 `valid`、`duplicate`、`not an issue` 或 `deferred`；状态使用 `open`、`fixed`、`accepted` 或 `deferred`。重复发现应关联原 ID；已经裁定的问题不得只因新一轮审查而重新打开，若有新证据或上下文变化，必须明确说明并更新裁定。启发式代码异味应标为判断建议，不与阻断交付的规范或规格缺陷混列。未解决的真实缺陷仍须修复或由用户明确接受，记录本身不构成豁免。

## 工作区模式

1. 记录完整基点 commit hash，并显式选择本次审查的已跟踪路径和要纳入的未跟踪路径。未跟踪重命名的旧路径、新路径都要纳入。拒绝把用户既有且与任务无关的差异带入审查；若无法区分则先澄清范围。
2. 用快照工具生成一次性完整补丁和状态摘要，向审查者传递该快照及现有裁定记录，而不是让审查者读取实时工作区。排除未选择、忽略及生成文件。
3. 先完成一轮完整的 Standards 与 Spec 双轴审查，将发现集中记录、裁定并成批修复。已确认、已裁定的问题若无新证据，不重复开启。
4. 修复后重新 capture 最终完整补丁并运行本地检查。最终验收总是核验完整新快照；复审范围按风险选择：局部、非行为改动复核修改 hunk 及其直接依赖；生命周期、并发、错误分类、消息准入、公共 API、程序集边界或规格范围改变时，重新进行完整双轴审查。任一复审发现新的实质问题时，修复后按受影响范围继续复核；不能用未验证的旧快照结论替代最终快照审查。
5. 报告基点、快照哈希、精确文件范围及验证结果。空补丁直接报告，不得为获得差异而暂存或提交。审查工具不得更改源码或暂存状态；提交仍需用户明确批准。

已提交提交范围的审查继续使用外部审查技能原有的固定点与提交差异流程，不由本文替代。

## 提交前审查与验收

实现完成后，在征求提交批准前审查最终快照并运行本地检查。根据改动风险按上述规则复核；完成最终快照验证后，再展示变更和拟提交信息并征求明确批准。没有明确批准不得创建提交。

工作区快照工具的自动化验收包括：暂存与未暂存改动同时存在且同一文件不重复、仅接受精确文件路径、拒绝文件到目录替换、路径元字符不按 glob 扩展、显式选择的未跟踪文件、忽略文件拒绝、未跟踪文件排除、已暂存删除后同路径未跟踪替换的完整捕获、空范围拒绝、删除、快照目录不覆盖、审查前后工作树或暂存区内容变化检测、裁定记录存在性与既有记录延续，以及本地检查按 CI 顺序运行并在首个失败处停止。审查流程仍须人工确认精确范围、裁定质量和风险对应的复审深度。
